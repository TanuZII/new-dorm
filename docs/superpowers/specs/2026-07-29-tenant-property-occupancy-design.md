# Tenant, Property, Reservation and Occupancy Design

## Goal

Deliver Milestone 2 as a complete vertical slice covering tenant registration, the physical dormitory hierarchy, bed or whole-room reservation, check-in, room transfer, occupancy history, and checkout request. Every slice includes schema, API, authorization, audit, responsive React UI, and automated acceptance evidence.

## Scope

This milestone includes:

- Student, personnel, and external tenant profiles
- Current/registered addresses, guardians, emergency contacts, faculty, major, and optional company information
- One internal tenant account linked to one tenant profile
- Buildings, floors, rooms, beds, and water/electric meter registrations
- Availability search by building, floor, date range, capacity, and status
- Bed reservation and exclusive whole-room reservation
- Reservation confirmation, cancellation, expiry, and check-in
- Current occupancy, room transfer, occupancy history, and checkout request
- Staff workspaces and tenant self-service read endpoints

Final checkout, debt clearance, damage billing, and deposit refund remain in Milestone 6. Contract generation remains in Milestone 3.

## Architecture Decision

Use an incremental normalized migration rather than extending the legacy `rooms.capacity` plus numeric `occupancies.bed_number` model. Flyway V4 introduces explicit buildings, floors, beds, reservations, allocation children, and occupancy events while retaining existing primary keys and migrating legacy room/occupancy rows. The migration must be repeatable only through Flyway history and must not require deleting `dbdorm`.

The backend remains a modular monolith. The `tenant`, `property`, `reservation`, and `occupancy` packages expose REST resources through `/api/v1`; business state changes live in transactional services, and JPA entities are not returned directly. React consumes typed DTOs through the shared cookie/CSRF API client and renders all staff routes inside the existing role-aware shell.

## Tenant Model

`tenants` keeps its numeric primary key and gains:

- `tenant_code`: generated by the application as `TEN-` plus a zero-padded database-backed sequence value, for example `TEN-000001`
- `tenant_type`: `STUDENT`, `PERSONNEL`, or `EXTERNAL`
- `institutional_id`: student/personnel identifier; nullable only for external tenants and unique when present
- `citizen_id`, title/master-data reference, Thai/English names, email, phone
- faculty and major master-data references for students
- company name, tax identifier, and document metadata for external corporate tenants
- `active`, `version`, created/updated timestamps

`tenant_addresses` stores `CURRENT` and `REGISTERED` addresses. `tenant_contacts` stores multiple `GUARDIAN` and `EMERGENCY` contacts with name, relationship, phone, and primary flag. `app_users.tenant_id` is nullable and unique so one login can be linked to at most one tenant.

No endpoint accepts a caller-provided `tenantCode`. Duplicate institutional identifiers return `TENANT_IDENTIFIER_DUPLICATE`.

## Property Model

The physical hierarchy is:

`buildings → floors → rooms → beds`

Each level has a stable code, Thai/English name where applicable, active flag, optimistic-lock version, and audit history. A room additionally has a room number, capacity derived from active beds, and readiness status:

- `AVAILABLE`
- `RESERVED`
- `OCCUPIED`
- `DAMAGED`
- `INACTIVE`

Beds have `AVAILABLE`, `RESERVED`, `OCCUPIED`, `DAMAGED`, or `INACTIVE`. Room status is recalculated from readiness plus current allocations; staff cannot manually mark an allocated bed available.

`room_meters` records `WATER` or `ELECTRIC`, serial number, installation/start date, and active state. Meter readings remain in the billing module.

## Reservation and Allocation Model

`reservations` is the header and contains tenant, requested date range, allocation scope (`BED` or `ROOM`), status, reason fields, optimistic-lock version, creator, and timestamps. `reservation_beds` contains every bed locked by the reservation. A whole-room reservation expands to all active beds in that room inside one transaction; it never creates a synthetic bed.

Reservation lifecycle:

`DRAFT → CONFIRMED → CHECKED_IN`

`DRAFT` or `CONFIRMED` may transition to `CANCELLED`; a confirmed reservation whose allowed check-in period passes may transition to `EXPIRED`. Cancellation requires a reason. Confirmation rechecks tenant activity, room readiness, every bed, and date overlap.

MySQL overlap protection uses three layers:

1. Lock all candidate bed rows in stable ID order.
2. Query overlapping confirmed reservations and open occupancy allocations inside the same transaction.
3. Insert one `bed_allocation_days` row per bed and calendar day for the finite reservation or expected occupancy range. Its primary key `(bed_id, allocation_date)` is the final database guard, so concurrent conflicting transactions cannot both commit. Each row references exactly one `reservation_bed` or `occupancy_bed`; cancellation, transfer, and checkout release only the affected future rows while allocation headers and events remain auditable.

Application and MySQL integration tests must prove that two concurrent attempts cannot both reserve the same bed or any bed in an exclusive room reservation.

## Occupancy Model

`occupancies` is the stay header and contains tenant, room, start/end dates, status, source reservation, version, and timestamps. `occupancy_beds` contains one bed for a bed rental or all room beds for an exclusive room rental. `occupancy_events` is append-only and records actor, event type, previous/new room, reason, timestamp, and audit trace.

Occupancy lifecycle:

`CHECKED_IN → CHECKOUT_PENDING → CHECKED_OUT`

A transfer closes the old bed allocations, validates and opens the new allocations, updates the stay, and appends a `TRANSFERRED` event in one transaction while the current occupancy remains `CHECKED_IN` in the destination. Checkout request changes the active stay to `CHECKOUT_PENDING`; final financial completion is deferred to Milestone 6.

## REST API

Tenant resources:

- `GET/POST /api/v1/tenants`
- `GET/PUT /api/v1/tenants/{id}`
- `PATCH /api/v1/tenants/{id}/status`

Property resources:

- `GET/POST /api/v1/buildings`; `PUT /api/v1/buildings/{id}`; `PATCH /api/v1/buildings/{id}/status`
- `GET/POST /api/v1/floors`; `PUT /api/v1/floors/{id}`; `PATCH /api/v1/floors/{id}/status`
- `GET/POST /api/v1/rooms`; `PUT /api/v1/rooms/{id}`; `PATCH /api/v1/rooms/{id}/status`
- `GET/POST /api/v1/beds`; `PUT /api/v1/beds/{id}`; `PATCH /api/v1/beds/{id}/status`
- `GET/POST /api/v1/room-meters`; `PUT /api/v1/room-meters/{id}`; `PATCH /api/v1/room-meters/{id}/status`
- `GET /api/v1/beds/availability?buildingId=&floorId=&from=&to=&scope=&capacity=&status=`

Reservation resources:

- `GET/POST /api/v1/reservations`
- `GET /api/v1/reservations/{id}`
- `POST /api/v1/reservations/{id}/confirm`
- `POST /api/v1/reservations/{id}/cancel`
- `POST /api/v1/reservations/{id}/check-in`

Occupancy resources:

- `GET /api/v1/occupancies`
- `GET /api/v1/occupancies/{id}`
- `POST /api/v1/occupancies/{id}/transfer`
- `POST /api/v1/occupancies/{id}/request-checkout`

Tenant self-service resources:

- `GET /api/v1/my/profile`
- `GET /api/v1/my/reservation`
- `GET /api/v1/my/occupancy`

All list endpoints support page, size, sort, and documented filters; global size is capped at 200. Mutations accept `version` where an existing aggregate is changed. State changes accept an explicit reason when cancellation, deactivation, transfer, or checkout is involved.

## Authorization and IDOR Protection

- `ADMIN`, `DORM_STAFF`: manage tenants, properties, reservations, and occupancies
- `FINANCE`: read the tenant and occupancy fields required for finance workflows
- `MAINTENANCE`: read buildings, rooms, beds, meters, and readiness status
- `TENANT`: access only `/api/v1/my/*`

Self-service controllers derive `tenantId` from the authenticated user relation. They never accept tenant or occupancy identifiers from request paths or query strings. Controller tests must change arbitrary IDs and prove another tenant's data is never returned.

## Error Contract and Audit

Errors retain the shared envelope: `code`, `message`, `fieldErrors`, `timestamp`, and `traceId`.

Milestone-specific codes:

- `TENANT_IDENTIFIER_DUPLICATE`
- `BED_NOT_AVAILABLE`
- `ROOM_NOT_READY`
- `CAPACITY_EXCEEDED`
- `INVALID_STATE_TRANSITION`
- `CONCURRENT_MODIFICATION`

The frontend preserves entered form values for validation failures. For `409`, it explains the conflict, reloads current availability/version, and requires the operator to review before retrying.

Every create, update, deactivate, confirm, cancel, check-in, transfer, and checkout request writes an append-only audit event. Cancellation, deactivation, transfer, and checkout events include the submitted reason.

## React Workspaces

### Tenant Registry — `/tenants`

Search by name, tenant code, institutional identifier, and type. Desktop uses a paged table; mobile uses record cards. Tenant details contain profile, addresses, contacts, linked account, and occupancy history sections. Create/edit uses an accessible multi-section form and never exposes tenant-code input.

### Property Map — `/properties`

Filter by building, floor, date range, status, and available-bed count. The hierarchy exposes status colors for available, reserved, occupied, damaged, and inactive resources. A room detail panel shows its beds, meters, current readiness, and the reason it cannot be allocated.

### Reservation Center — `/reservations`

Use a four-step wizard: select tenant; choose dates and bed/room scope; select an available allocation; review and confirm. Availability displayed by the browser is advisory. The backend always locks and revalidates at confirm/check-in.

### Occupancy Center — `/occupancies`

Provide check-in queue, current residents, transfer action, checkout-request action, and an append-only timeline. State actions are absent when the current status does not allow them.

All workspaces include loading, empty, error, pagination, keyboard-focus, reduced-motion, desktop, and 390 px mobile states. Navigation is visible only to allowed roles and no menu item is a dead end.

## Testing and Acceptance

Backend tests include:

- Tenant code generation and duplicate institutional identifier
- State-transition unit tests
- Repository/date-overlap tests
- MySQL integration tests for concurrent bed reservation, exclusive-room reservation, check-in, and atomic transfer
- Authorization tests for every staff role
- IDOR tests for `/my/*`
- Audit reason and trace tests

Frontend tests include:

- Role-aware routes and navigation
- Results, loading, empty, validation, server error, and conflict states
- Reservation wizard blocking invalid progress
- Mobile record-card and action visibility contracts

Browser acceptance runs all four staff routes at desktop and 390 × 844. Acceptance requires:

- One bed cannot have overlapping confirmed reservations or open occupancies.
- A damaged/inactive room or bed cannot be reserved.
- Whole-room reservation locks every active bed atomically.
- Transfer releases old allocations and opens new allocations atomically while preserving history.
- Checkout cannot bypass `CHECKOUT_PENDING` or the later financial workflow.
- A tenant cannot obtain another tenant's profile, reservation, or occupancy by changing an identifier.

Each implementation task ends with targeted tests, full relevant regression tests, production build where UI changes, `git diff --check`, commit, and push to `origin/main`.
